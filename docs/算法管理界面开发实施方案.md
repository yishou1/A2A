# 算法管理界面开发实施方案

## 1. 方案定位

本方案基于以下内容制定：

- `docs/算法管理界面设计文档.md`
- `docs/算法管理界面功能说明（甲方版）.md`
- 当前 C++ Registry、HTTP Server、Runner Cache、Model Loader 和 Execution Logger 实现
- 当前 43 个算法包、28 个 KC 业务功能点及 ONNX / Python HTTP 两种后端

第一版界面定位为内网中的“算法资产管理与调用控制台”，以高密度桌面管理为主，不做宣传型卡片首页。核心闭环是：

```text
纳管 → 验证 → 激活 → 登记部署/预加载 → 在线调用 → 链路定位 → 禁用/卸载/删除
```

不纳入第一版的范围：模型训练、数据标注、网页修改模型/算法源文件、云资源开通、容器集群建设、全量执行历史分析和自动扩缩容。

## 2. 当前项目基线

### 2.1 已具备的后端能力

| 能力 | 当前实现 |
|---|---|
| 服务健康 | `GET /health` |
| 算法查询 | `GET /algorithms`、`GET /algorithms/{id}/{version}/{backend}` |
| 算法纳管 | 服务器本地路径注册 |
| 生命周期 | validate、activate、disable、逻辑 delete |
| 部署记录 | 新增、删除、更新状态 |
| 运行资源 | load、unload、Runner Cache |
| 统一调用 | `POST /run`，支持 `deploy_id` 和 `function_context` |
| 业务功能 | 28 个 KC 功能点目录和算法映射 |
| 链路追踪 | 按已知 `trace_id` 读取功能执行记录 |

现有 C++ Debug 基线已通过 `ctest --test-dir build -C Debug`（1/1）。仓库内尚无 Web 前端工程或 Node 包管理文件。

### 2.2 必须正确表达的状态

界面不将以下状态合并为一个“可用/不可用”标签：

1. **注册表生命周期**：`draft / validated / active / disabled / deleted`。
2. **算法卡声明状态**：算法包资料自身的成熟度。
3. **部署记录状态**：`loading / ready / error / unloaded`。
4. **Runner 内存状态**：当前仅 `/health.runner_cache_size` 提供全局数量，无法确定单个算法是否已缓存。

当前 `/run` 会对 `active` 算法按需创建 Runner，因此第一版的操作口径为：

- `active` 表示“允许发起调用”，不代表外部服务必然健康。
- `ready` 表示某条部署记录已就绪。
- “已预加载”在后端提供按算法/`deploy_id` 的 Runner 状态前，不做确定性展示。
- 在线调用对 `active` 开放，调用可能触发首次加载，界面必须明确提示。

## 3. 产品信息架构

```text
算法管理台
├── 运行总览                         /overview
├── 算法目录                         /algorithms
│   └── 算法详情                     /algorithms/:id/:version/:backend
├── 部署管理                         /deployments
├── 在线调用                         /invoke
├── 功能点矩阵                       /functions
└── 执行链路                         /traces
```

“系统设置”第一版不设独立导航，因当前后端没有可写设置 API。注册表路径、审计日志路径、功能目录路径和 Runner 数量作为总览页的只读“服务信息”展示。

## 4. 页面与交互设计

### 4.1 全局框架

- 左侧固定导航，顶部显示服务连接状态、最后刷新时间和手动刷新。
- 桌面端优先，建议最小有效宽度 1280px；窄屏支持浏览，不承诺复杂部署表单的移动端操作体验。
- 连接中断时保留最近一次查询结果，加上“数据已过期”遮罩，禁用所有变更操作。
- 所有列表筛选写入 URL Query，便于刷新、返回和分享定位。

### 4.2 运行总览

顶部指标：算法总数、active、validated、disabled、draft、部署总数、ready、error、Runner Cache 数量。

下方两个工作区：

- **分布摘要**：ONNX / Python HTTP 数量、任务族数量。
- **需处理项**：部署 `error`、active 但无 ready 部署、draft、Python 外部依赖。这些是风险线索，不将“active 但无 ready 部署”直接判定为不可调用。

数据源为 `/health` 和 `/algorithms?active_only=false`，第一版由前端汇总。

### 4.3 算法目录

主表默认列：

| 列 | 展示 |
|---|---|
| 名称 | `display_name`，副标题 `algorithm_id` |
| 版本 | `version` |
| 后端 | ONNX / Python HTTP |
| 任务族 | `task_family` |
| 注册状态 | 只使用 Registry status |
| 部署 | `ready 数 / 总数`，error 单独标红 |
| 能力 | 前 2 项 + 其余数量 |
| 主操作 | 随生命周期变化 |

可选列：主性能指标、P50 时延、最低 CPU/内存/显存。

筛选区分两层：

- 常用：关键字、注册状态、任务族、后端、能力、功能点。
- 高级：节点、最大 CPU/内存/显存。

关键字、排序和分页在数量较少时先由前端处理。前端每次明确发送 `active_only=false`，避免落入后端默认只返回 active 的行为。

### 4.4 算法详情

顶部信息带显示唯一键、Registry status、Card status、部署摘要和主操作。下方标签页：

1. **概览**：摘要、适用/不适用场景、模态、能力、约束、安全等级。
2. **输入输出**：完整 Schema、字段表和卡片样例。
3. **性能资源**：登记指标、复杂度、模型规模和资源要求，明确标注“非实时监控”。
4. **功能点**：KC 编号、角色和覆盖程度。
5. **部署实例**：详细列表与部署操作。
6. **在线调用**：复用调用工作台。
7. **算法卡**：结构化视图和原始 JSON。

页面路由中的 ID、version 和 backend 必须分别做 URL 编码，禁止通过字符串拼接产生 API 路径。

### 4.5 纳管和生命周期

- 注册抽屉只接受“服务器可访问路径”，不伪装成浏览器本地上传。
- 注册成功进入 `validated`，跳转详情后提供独立的“激活”操作，不自动激活。
- 验证前说明“重读算法卡/Schema，保留部署记录”。
- 禁用、删除使用二次确认；删除要求输入 `algorithm_id`。
- 删除结果文案使用“已逻辑删除注册记录”，不使用“已永久删除文件”。

操作按钮使用前端状态机显示，后端 409 仍作为最终准绳。

### 4.6 部署管理

全局部署页将所有算法的 `deployments` 扡平化为列表；详情页复用同一列表并限定算法唯一键。

操作规则：

- 新增部署初始为 `unloaded`。
- `load` 表单按 backend 分支：ONNX 显示传输参数；Python HTTP 显示连接池参数。
- 当前 `/load` 是同步接口，界面只能表示“请求处理中”，不伪造上传或加载进度。
- 卸载、删除部署均二次确认。`ready` 部署的主路径为先 unload，再删除登记。
- 第一版不提供 endpoint/node/zone 的伪编辑；如需修改，明确提示删除后重建。

### 4.7 在线调用

左侧为请求编辑器，右侧为结果，支持左右拖动尺寸；窄屏改为上下布局。

模式：

- **表单模式**：根据完整 JSON Schema 生成。仅有字段摘要时，表单模式降级为简单标量字段。
- **JSON 模式**：编辑 `inputs`、`params` 和可选 `function_context`，作为所有算法的保底调试方式。

`request_id` 和 `trace_id` 默认由前端使用 `crypto.randomUUID()` 生成，可重新生成；不持久化原始输入输出。完整请求预览会在发送前通过 AJV 验证 `inputs`，后端仍进行最终验证。

调用请求不自动重试。结果展示 HTTP 状态、`ok`、`outputs`、`usage`、`error`、唯一键、request ID、trace ID 和 `function_execution`。

### 4.8 功能点矩阵

默认按 KC-01～KC-28 显示，支持按 OODA 阶段和 F2T2EA 阶段分组。每行展示功能点、关联算法数量、角色、覆盖程度、Registry status 和 ready 部署数。

当前需要将 `/operational-functions` 与全量算法列表在前端 join。不对 28 个功能点分别发起查询。

### 4.9 执行链路

第一版只有一个 `trace_id` 输入框和查询按钮，不展示不存在的“最近执行列表”。结果使用纵向时间线，展示 sequence、功能点、算法唯一键、执行状态、latency、error code 和步骤标识。

## 5. 前端技术方案

### 5.1 技术选型

| 领域 | 选型 |
|---|---|
| 工程 | React + TypeScript + Vite |
| 路由 | React Router |
| 服务端状态 | TanStack Query |
| UI | Ant Design，使用紧凑主题 |
| 表单 | React Hook Form |
| Schema 验证 | AJV |
| JSON 编辑 | Monaco Editor 动态加载；首屏不打包 |
| 单元/组件测试 | Vitest + Testing Library + MSW |
| 端到端 | Playwright |

不引入 Redux。服务端数据交给 TanStack Query，筛选交给 URL，弹窗和编辑器状态保留在局部组件。

### 5.2 目录结构

```text
web/
├── package.json
├── vite.config.ts
├── src/
│   ├── app/                 # 路由、QueryClient、主题、全局错误边界
│   ├── api/                 # HTTP client、contracts、query keys
│   ├── components/          # 跨功能通用组件
│   ├── features/
│   │   ├── overview/
│   │   ├── algorithms/
│   │   ├── deployments/
│   │   ├── invocation/
│   │   ├── functions/
│   │   └── traces/
│   ├── lib/                 # 状态机、格式化、脱敏和 Schema 工具
│   ├── mocks/               # MSW fixtures/handlers
│   └── test/
└── e2e/
```

### 5.3 API 层原则

- 所有三元组路径由统一 `algorithmPath(key)` 生成。
- 使用 `ApiError` 保留 HTTP status、`error_code`、`message`、request/trace ID。
- 查询缓存键全部包含筛选和算法三元组。
- 生命周期、部署、load/unload 成功后，invalidate 算法列表、详情、总览和部署列表。
- 查询类网络错误最多重试 1 次；变更和 `/run` 不自动重试。
- 开发环境使用 Vite `/api` 代理到 `127.0.0.1:8088`；生产环境使用同源网关将 `/api/*` 转发到 AlgoLib，前端不直连公网 C++ 端口。

## 6. 开发前必须对齐的后端契约

### P0：不处理就无法完整实现第一版

1. **列表增加 Registry status**  
   `GET /algorithms` 当前返回 `agent_view`，其中没有注册表 `status`。建议增加 `registry_status` 和 `card_status`，不要让前端逐行调详情。

2. **提供完整输入/输出 Schema**  
   当前 `input_schema_summary` 只包含 title/type/required 和顶层字段的 name/type/description，无法表达嵌套数组、items、enum、边界和 additionalProperties。建议新增：

   ```http
   GET /algorithms/{id}/{version}/{backend}/schemas/input
   GET /algorithms/{id}/{version}/{backend}/schemas/output
   ```

   返回 `application/schema+json`，并继续在服务端校验路径边界。

3. **提供同源接入方式**  
   开发阶段由 Vite 代理处理；部署阶段需要 Nginx/网关配置。如确实要前后端分域，再为 C++ Server 增加受控 CORS 白名单，不使用 `*`。

4. **详情响应脱敏**  
   当前详情 `entry` 含 `package_root`、`card_path`、runtime endpoint 等完整内部信息。应在后端管理视图中隐去 URL userinfo、query、fragment 及可能的凭据，并由网关限制管理界面访问。

### P1：可以并行开发，但上线前应补齐

1. 统一错误结构和请求关联 ID；当前管理错误只有 `error_code/message`。
2. 非法 query 参数应返回 400，当前部分 status/backend/数值解析失败会被静默忽略。
3. 增加按算法和 `deploy_id` 查询 Runner 是否已加载的管理端点，使“已预加载”可被真实展示。
4. 删除部署记录时应拒绝已加载实例，或同步失效对应 Runner Cache；当前删除路由没有失效指定 `deploy_id` 的 Runner。
5. 明确 load/unload 与部署状态的一致性失败处理。
6. 当前 HTTP Server 在同一全局 mutex 中执行加载和 Python 网络调用。长耗时 `/load` 或 `/run` 可能阻塞健康和管理查询；在正式并发使用前需缩小锁粒度或引入异步任务。

### P2：增强项

- 算法包上传、隔离解压、预校验和安全扫描。
- 算法卡 PATCH、字段白名单、并发版本和备份。
- 部署实例完整 PATCH。
- 执行历史分页、时间筛选、聚合统计和导出。
- 异步加载进度、外部服务健康代理和告警。

## 7. 实施切片

### Slice 0：契约和工程骨架

**后端**

- 为列表添加 `registry_status/card_status`，添加 Schema 端点及对应 C++ HTTP 测试。
- 确定 `/api` 反向代理约定。

**前端**

- 建立 `web/` 工程、主题、路由、API client、类型、MSW 和测试骨架。
- 实现 AppShell、服务可达性和统一错误展示。

**完成标志**：前端可通过代理读取真实 `/health` 和全量算法，TypeScript 契约测试通过。

### Slice 1：只读管理面

- 运行总览、算法列表、筛选、详情六个只读区域。
- 功能点矩阵和全局部署列表的只读视图。
- 加载、空、错误、过期数据状态。

**完成标志**：可用仓库的多种算法卡验证复杂 Schema、缺失可选指标、无部署和多部署场景。

### Slice 2：生命周期与部署变更

- 服务器路径注册、验证、激活、禁用和逻辑删除。
- 部署新增、状态更新、load、unload 和删除。
- 状态机、影响提示、二次确认和操作后刷新。

**完成标志**：注册 → 激活 → 部署 → 预加载 → 禁用 → 卸载 → 逻辑删除的 E2E 通过，实际后端状态与界面一致。

### Slice 3：在线调用与链路

- Schema 表单、JSON 模式、部署选择和功能上下文。
- 结果、usage、错误和复制功能。
- 按 trace ID 查询的执行时间线。

**完成标志**：ONNX 和 Python HTTP 各至少一个真实算法完成调用，Schema 错误、服务未就绪、超时和输出校验错误能正确展示。

### Slice 4：硬化和交付

- 交互细节、键盘操作、无障碍标签、性能和大 JSON 优化。
- 生产构建、同源网关样例、离线安装策略和部署说明。
- 完整 Playwright 关键路径。

## 8. 测试策略

### 8.1 合约与单元测试

- API JSON 解析：完整、缺失可选字段和非法枚举。
- 生命周期可用操作矩阵。
- 部署摘要和总览聚合。
- URL 编码、错误归一化和 endpoint 脱敏。
- JSON Schema 表单对 string/number/integer/boolean/enum/object/array 的基本映射。

### 8.2 组件测试

- 四种非 deleted 生命周期的按钮和禁用规则。
- 服务不可达时变更按钮全部禁用。
- 高风险操作确认内容和二次输入。
- 详情、部署、功能点和 trace 空状态。
- 在线调用不自动重试且不写 localStorage。

### 8.3 E2E 主路径

1. 打开总览并查看服务健康。
2. 以服务器路径注册算法，查看详情并激活。
3. 添加部署、预加载、在线调用、复制 trace ID 并查询链路。
4. 禁用、卸载、删除部署和逻辑删除算法。
5. 验证服务断开、400/409/422/503/504 和长耗时请求。

## 9. 建议的开发起点

首个开发切片建议同时完成以下最小纵向链路：

1. 后端为算法列表补齐 `registry_status/card_status`。
2. 后端提供完整 input/output Schema 端点。
3. 新建 `web/` 工程和 `/api` 开发代理。
4. 实现 AppShell、健康状态、算法列表和详情基础页。
5. 用真实 C++ Server 完成一条查询型 E2E，再进入生命周期变更开发。

这个起点可以在不依赖模型训练、外部 API 凭据或完整部署环境的前提下，尽早验证前后端契约和整体交互方向。
