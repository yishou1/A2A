## 二、Agent 与主体架构对接梳理

### 2.1 对接原则

业务 Agent（TIA、任务调度等）只负责：

1. 向 Nacos 注册（`serviceName=A2A-Agent`）并维持心跳  
2. 暴露标准 A2A HTTP（`/sendMessage`、`/health`、`/ready`、agent-card）  
3. 按 `required_skill` / 算法计划调用自身算法或算法库  
4. 返回统一 task response，并用 `work_item` 做幂等  

Commander 负责 BPEL 编排、skill 匹配、租约 `busy/idle`、failover、checkpoint。

### 2.2 心跳机制（主体控制面）

注册后由 `AgentHeartbeatSupervisor` 按约 **5 秒** 向 Nacos 发送 beat，并刷新：

- `heartbeat_ts` / `heartbeat_at`：存活判定  
- `agent_run_state`、`task_execution_status`、`active_tasks`  
- 资源与算法部署状态（若接入 `ResourceMonitor` / `ModelRegistry`）  

**关键约束：** 心跳不得覆盖 Commander 写入的 `lease_*` 与 `status=busy|unavailable`。

TIA 本地注册示例（`tactical_intelligence_agent/main.py`）：

```python
registry.register_service(
    service_name=os.environ.get("TIA_NACOS_SERVICE", "A2A-Agent"),
    ip=ip,
    port=port,
    metadata={"role": role, "status": "idle"},
    heartbeat_interval=heartbeat_interval,  # 默认 5s
)
```

### 2.3 算法库调用两条路径

```text
路径 A（单算法）：algolib / curl → POST :902x/predict
路径 B（Agent 编排）：Commander → Agent → factory/client → POST /run 或 /predict
```

TIA 默认 `execution_mode: algorithm_library`，通过 `AlgorithmLibraryClient` 调用，Agent 进程不直接加载大模型权重。

## 三、TIA 算法预训练 / 迁移学习盘点

### 3.1 结论

**不是 11 个算法都已领域预训练好。** 可粗分为三类：

| 类型 | 代表算法 | 本周是否继续训 |
|------|----------|----------------|
| 公开预训练 + 已域迁移 | RT-DETR（`battlefield_rtdetr.pt`）、MOTR（VisDrone）、MARL-PPO 调度 | **先不管** |
| 公开骨干够用 | ImageBind/CLIP、Flan-T5、MiniLM | **先不管** |
| 随机初始化辅助头 | **ODConv、EDL、Mamba、SupCon、路由** | **本周重点训了前三项中的 ODConv/EDL/SupCon** |

随机头直接上真实场景的问题：流程能跑，但置信度精炼、敌我分类等决策字段不可信（尤其 SupCon）。

### 3.2 本周锁定的「仍需训练」与数据需求

| 算法 | 需要的数据类型 |
|------|----------------|
| SupCon 敌我分类 | 目标裁剪图 + `friendly/neutral/hostile/unknown` |
| ODConv 置信度精炼 | 战场图 + bbox + 是否真目标 |
| EDL 证据验证 | 检测候选 + `verified=0/1`（可与 ODConv 共用） |

公开「敌我」航拍标注极少，因此采用 **`datasets/battlefield` + 场景代理标签** 做 bootstrap。

## 四、数据集构造与辅助头训练

### 4.1 数据准备脚本

脚本：`scripts/prepare_tia_aux_datasets.py`  

一次生成两类数据到 `datasets/tia_aux/`：

| 数据集 | 规模（本次） | 路径 |
|--------|--------------|------|
| IFF 裁剪 | 34560（F/H/N/U 四类） | `datasets/tia_aux/iff_crops/` |
| 检测真假 | 38000（正 34560 / 负 3440） | `datasets/tia_aux/det_verify/` |

敌我代理标注逻辑（非真实交战归属，用于把管线跑通）：

```python
def assign_iff_label(class_id: int, image_stem: str, rng: random.Random) -> str:
    """
    - storage-tank → neutral
    - small-vehicle → neutral/unknown 为主
    - plane/ship/helicopter/large-vehicle → 按图像哈希分红蓝 → friendly/hostile
    - 约 8% 强制 unknown
    """
    ...
```

检测真假：GT 框为正样本；与 GT IoU &lt; 0.3 的随机框为负样本（可选 `--run-detector` 用 RT-DETR 补真实 FP）。

### 4.2 训练脚本与结果

| 脚本 | 模型 | 验证指标 | 权重路径 |
|------|------|----------|----------|
| `scripts/train_odconv_edl.py` | ODConv + EDL | EDL acc ≈ **99.6%**，ODConv MAE ≈ **0.13** | `odconv_refiner.pt` / `edl_head.pt` |
| `scripts/train_supcon_meta.py` | SupConMetaNet + ResNet18 投影 | val acc ≈ **39.6%** | `supcon_meta.pt` + `supcon_crop_encoder.pt` |

SupCon 准确率偏低的原因：代理敌我标签按图哈希分配，**同一外观类别可能标成不同阵营**，视觉上不可分。后续有真实敌我标注后应重训。

训练命令示例：

```powershell
.\.venv\Scripts\python.exe scripts/prepare_tia_aux_datasets.py --negatives-per-image 8
.\.venv\Scripts\python.exe -u scripts/train_odconv_edl.py --epochs 15 --batch-size 64
.\.venv\Scripts\python.exe -u scripts/train_supcon_meta.py --epochs 15 --batch-size 64 --max-train-samples 8000
```

## 五、任务调度 Agent：对齐 lzh 小模型动态调算法库

### 5.1 背景

TIA 已按 lzh 方式实现：

```text
ENABLE_LLM → chat_json 选算法 → GET /algorithms → POST /run
```

本周把**独立的** `task_scheduling_agent` 做成**完全同一套机制**（提交 `f117e0b`）。

### 5.2 核心链路

```text
AMOS JSON
   │
   ├─ ENABLE_LLM=true → OpenAICompatibleClient.chat_json
   │                      （白名单仅 marl_ppo_task_scheduler）
   │
   ├─ ENABLE_LLM=false → 默认算法 marl_ppo_task_scheduler
   │
   ▼
强制覆盖 inputs = amos_to_algolib_inputs(AMOS)   # 防 LLM 幻觉改态势
   │
   ▼
AlgorithmLibraryClient.predict / POST {ALGOLIB}/run
   │
   ▼
sensor_assignments + reattack_plan + llm_plan
```

### 5.3 关键代码说明

#### （1）后端切换

`task_scheduling_agent/engine.py`：配置/环境走 algolib 时不再本地硬跑。

```python
def run_schedule(amos_payload, *, use_mock=True, config=None):
    cfg = config or {}
    from task_scheduling_agent.algolib_runtime import run_with_algolib, use_algolib_backend

    if use_algolib_backend(cfg):
        return run_with_algolib(amos_payload, config=cfg)

    # 否则：本地 mock / MARL-PPO
    situation = situation_from_amos(amos_payload)
    ...
```

`TASK_SCHEDULING_BACKEND=algolib` 或 CLI `--algolib` 即启用。

#### （2）AMOS → 算法库输入（并强制覆盖 LLM inputs）

```python
def amos_to_algolib_inputs(amos_payload: dict) -> dict:
    situation = situation_from_amos(amos_payload)
    # tracks / detections / frames / batch_context
    # + amos_payload 原样附带，供服务端可选直连适配
    return {
        "amos_payload": amos_payload,
        "tracks": tracks,
        "detections": detections,
        "frames": frames,
        "batch_context": batch_context,
    }
```

规划阶段无论 LLM 在 `algorithm_calls[].inputs` 里写了什么，运行时都会：

```python
raw_call = {**raw_call, "inputs": real_inputs}  # real_inputs 来自真实 AMOS
```

与 lzh `algolib_runtime._select_algorithm_call` 的「用完整请求覆盖」一致。

#### （3）小模型 Prompt（只选算法，不编造调度结果）

`task_scheduling_agent/llm/prompts.py`：

```text
You MUST select marl_ppo_task_scheduler when it is available.
Do NOT invent schedule assignments, platform IDs, or target IDs in the plan.
leave inputs empty (the runtime will inject the real AMOS payload).
```

返回 JSON 形状与 TIA / lzh 决策 Agent 相同：`intent` + `algorithm_calls[]` + `explanation`。

#### （4）网关目录暴露调度算法

TIA 管线故意不含 `marl_ppo_task_scheduler`。本周在 `catalog.build_algorithm_catalog(include_scheduling=True)` 与网关 `_active_registry()` 中把它加回 `/algorithms`，供调度 Agent 发现。

### 5.4 CLI 用法

```powershell
# 固定默认算法（无 LLM）
.\.venv\Scripts\python.exe -m task_scheduling_agent `
  --input examples/amos_schedule_inputs/sample_amos_request.json `
  --output data/output/task_schedule/amos_algolib.json `
  --algolib

# 小模型动态选算法
$env:ENABLE_LLM="true"
$env:TOOL_LLM_URL="http://127.0.0.1:11434/v1"
$env:TOOL_LLM_NAME="qwen2.5:7b"
.\.venv\Scripts\python.exe -m task_scheduling_agent `
  --input examples/amos_schedule_inputs/sample_amos_request.json `
  --algolib --llm
```

前置：算法服务（至少 `:9024`）+ `tia_algolib_gateway`（`:8088`）。

### 5.5 测试

`tests/test_task_scheduling_algolib.py` 覆盖：

- AMOS → algolib inputs 字段完整性  
- 无 LLM 时走默认 `marl_ppo_task_scheduler`  
- 有 LLM 时选中算法且 **伪造 inputs 被覆盖**  
- Agent `backend=algolib` 路由  

与原有 AMOS adapter 测试合计 **10/10 通过**。
