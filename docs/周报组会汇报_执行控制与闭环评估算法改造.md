# 执行控制与闭环评估算法改造周报

**汇报周期：** 2026年9月第2周  
**汇报人：** 待填写  
**涉及模块：** 执行控制、闭环评估、通用算法库、Commander调用适配

## 一句话概括

这周主要做了三件事：把执行控制和闭环评估中的算法从 Agent 业务代码里拆出来；把几项自研基础算法替换成成熟开源实现；再按部署资源划分成低、中、高三档。改完以后，原来的业务链路、输入字段和输出结果格式没有变化，但算法可以单独维护、单独测试，也更方便以后同步到 GitHub 算法库分支。

## 本周主要改动

| 改造内容 | 改造前 | 改造后 | 主要目的 |
|---|---|---|---|
| 算法与 Agent 的关系 | 算法逻辑和 Agent 编排混在一起 | 通用算法放到独立算法库，Agent 只负责收集和传递数据 | 后续替换算法时不影响整条业务链路 |
| 轨迹预测 | 项目内手写线性拟合 | scikit-learn 线性回归、FilterPy 卡尔曼滤波 | 提高噪声场景下的预测稳定性 |
| 关联规则挖掘 | 项目内手写 Apriori 风格实现 | mlxtend `apriori` | 使用成熟实现，降低维护成本 |
| 任务完成度评估 | 手写随机森林，共19棵树 | scikit-learn 随机森林，共192棵树 | 提高模型稳定性，支持分档运行 |
| 算法运行配置 | 只有一套固定配置 | `low`、`medium`、`high` 三档 | 兼顾低资源设备、默认部署和高精度场景 |
| 链路验证 | 以单模块测试为主 | 增加三档完整链路测试 | 确认算法替换后上下游仍然连通 |

## 改造后的整体链路

```text
前置 Agent 已有输出
        |
        v
执行控制适配层
  - 汇总轨迹、威胁、计划、资源和授权信息
  - 选择 low / medium / high 档位
        |
        v
通用执行控制算法
  - mlxtend 关联规则匹配
  - scikit-learn / FilterPy 轨迹预测
  - 生成动作、执行器和控制命令
        |
        v
执行结果及前置 Agent 结果
        |
        v
闭环评估适配层
  - 整理七维任务特征
  - 检查真实输入是否完整
        |
        v
通用闭环评估算法
  - xBD 毁伤评估
  - scikit-learn 随机森林完成度评分
  - 闭环建议器生成继续、调整、补充侦察或终止建议
```

这里最重要的一点是，算法只使用前置 Agent 已经提供的数据，不会为了让模型运行而随意补造感知、威胁或通信结果。如果某项输入确实缺失，系统会保留缺失状态并返回诊断信息，避免默认值把真实问题掩盖掉。

## 算法是怎么解耦的

改造前，轨迹预测、规则匹配和完成度评估的一部分实现直接放在 Agent 内部。后面想更换算法时，往往还要同时修改 Agent 的数据处理和调用逻辑，影响范围比较大。

现在把通用算法统一放到了 `algorithmrepo/services/a2a_algorithms_common/`。这一层只认识结构化的 `inputs` 和 `params`，不依赖 Commander、A2A 通信、FastAPI 或某一个具体 Agent，所以既能作为普通 Python 模块使用，也能作为独立 HTTP 服务启动。

Commander 侧的 `execution_control_agent/algolib_runtime.py` 和 `closed_loop_agent/algolib_runtime.py` 现在属于适配层。它们负责把前置结果整理成算法需要的格式、选择运行档位、调用算法服务、检查返回结构，并在远程服务不可用时切换到本地算法副本。

| 层级 | 现在负责什么 | 不再负责什么 |
|---|---|---|
| Agent / Commander | 收集前置结果、业务编排、算法调用、结果校验和异常处理 | 不再直接实现随机森林、卡尔曼滤波、Apriori 等底层算法 |
| 通用算法库 | 接收结构化输入、执行计算、返回结构化结果 | 不关心 Agent 通信和任务编排 |
| 算法服务接口 | 把通用算法包装成可独立部署的服务 | 不改变算法内部业务含义 |

Commander 中仍保留一份相同的算法代码用于离线回退，同时增加了 `scripts/check_zh_algorithm_vendor.ps1`。这个脚本用于检查算法库主版本和 Commander 本地副本是否一致，避免后续只更新了一边，导致远程调用和本地回退给出不同结果。

## 执行控制算法替换

### 轨迹预测

原来的轨迹预测是项目内手写的普通最小二乘直线拟合。它可以根据历史坐标估算移动方向，但对观测抖动、噪声和连续状态更新的处理能力有限。

现在低档使用 scikit-learn 的 `LinearRegression`，中档和高档使用 FilterPy 的常速度卡尔曼滤波。卡尔曼滤波可以简单理解为：先根据目标上一时刻的位置和速度预测下一步，再用最新观测值进行修正。观测不稳定时不会完全相信当前坐标，目标运动发生变化时也会持续更新状态，因此更适合连续轨迹预测。

| 项目 | 采用方案 | 选择原因 | GitHub情况（截至2026-09-11） |
|---|---|---|---|
| 线性回归与随机森林 | [scikit-learn](https://github.com/scikit-learn/scikit-learn) | Python机器学习领域常用库，接口和测试体系成熟 | 约67.2k Star |
| 卡尔曼滤波 | [FilterPy](https://github.com/rlabbe/filterpy) | 提供成熟的 Kalman Filter 实现，适合状态估计和目标跟踪 | 约3.9k Star |

替换后没有改变下游需要的字段，仍然返回目标速度、预测瞄准点、执行时间、预测时间和拟合质量。也就是说，内部计算方法升级了，但命令生成模块不需要跟着重写。

在同一套160条合成轨迹基准上，位置 RMSE 从0.964136下降到0.909958。这个结果说明新方案在当前测试数据上的整体预测误差更低，但合成数据测试主要用于比较新旧实现，后续还需要真实轨迹继续验证。

### 关联规则挖掘

执行控制会根据历史样本寻找“什么条件通常对应什么动作”，例如任务类型、威胁等级和目标状态同时出现时，通常选择哪一种动作或执行器。原来这部分的频繁项集搜索是项目内手写实现，现在替换成 mlxtend 的 `apriori`。

这次只替换了 Apriori 的通用计算底座，项目自己的后件投票、规则匹配、授权门禁、执行器选择和命令生成逻辑都保留了。因此替换前后仍然生成28条规则，模型文件哈希也保持一致，说明业务规则没有因为底层库变化而被改写。

[mlxtend](https://github.com/rasbt/mlxtend) 截至2026年9月11日约有5.2k Star，已经提供事务编码、Apriori 和频繁项集分析等成熟能力。选择它主要是为了减少手写算法的维护和边界处理成本，不是为了改变现有执行规则。

## 闭环评估算法替换

任务完成度评估原来使用项目内手写随机森林，共19棵树。本次替换成 scikit-learn 的 `RandomForestRegressor`，完整模型包含192棵树。

随机森林可以理解为“让多棵决策树分别判断，再综合大家的结果”。每棵树训练时看到的样本和特征会有差异，所以不会完全按照同一条判断路径工作。最后对多棵树的输出进行综合，可以降低单棵树偶然判断错误或过拟合的影响。

模型输入仍然是闭环评估的七维任务特征：毁伤效果、资源就绪程度、控制及时性、情报可靠性、当前威胁压力、弹药或资源压力以及通信质量。模型输出任务完成度分数，闭环建议器再结合任务状态、风险和输入完整性，给出继续执行、调整方案、补充侦察或终止等建议。

| 模型参数 | 当前配置 | 作用 |
|---|---:|---|
| 决策树总数 | 192 | 形成较稳定的完整模型，并支持三档抽取 |
| 最大深度 | 10 | 防止树无限生长和过度记忆训练数据 |
| 叶节点最少样本数 | 12 | 避免少量样本形成过于特殊的判断条件 |
| 特征抽样 | 平方根抽样 | 让不同树学习不同特征组合，增加模型差异性 |
| 样本抽样 | Bootstrap | 每棵树使用不同的有放回训练样本 |

树并不是越多越好。树数增加到一定程度后，结果会逐渐稳定，继续增加树带来的精度提升很小，但计算时间和内存还会继续增加。当前选择192棵，是因为它可以比较方便地拆成低档32棵、中档96棵和高档192棵，同时兼顾当前数据规模和推理开销。这是目前的工程配置，不代表所有数据集的固定最优值。

训练时按照 `replay_id` 将数据分为70%训练集、15%验证集和15%测试集，同一场回放不会同时进入训练集和测试集。测试过程中发现，数据表中原有的部分派生特征已经间接包含比赛结果，如果直接使用会得到接近100%的虚高准确率。因此本次没有使用这些泄漏结果的字段，而是从原始 MMR、APM、持续时间和对手 MMR 等基础字段重新构造代理特征，并把比赛结果排除在模型输入之外。

| 指标 | 旧模型 | 新模型 | 结果说明 |
|---|---:|---:|---|
| 测试准确率 | 0.5743 | 0.5951 | 有小幅提升 |
| R2 | 0.0387 | 0.0745 | 拟合能力有所改善，但仍然有限 |
| 平衡准确率 | 未记录 | 0.5951 | 正负样本判断相对均衡 |

这里需要说明，当前训练使用的是 SC2LE 代理数据，所以这些数字只能证明新实现比旧代理模型有所改善，不能直接当作真实业务场景的生产准确率。后续拿到真实标注数据后，还需要重新训练和校准。

## 低、中、高三档配置

| 档位 | 执行控制输入规模 | 轨迹预测 | 完成度随机森林 | 建议使用场景 |
|---|---|---|---:|---|
| `low` | 最多16条轨迹、3条匹配规则 | scikit-learn 线性回归 | 32棵树 | CPU资源有限、边缘设备、快速演示 |
| `medium` | 使用完整输入 | FilterPy 卡尔曼滤波，过程噪声0.05、观测噪声1.0 | 96棵树 | 默认部署，兼顾速度和稳定性 |
| `high` | 使用完整输入 | FilterPy 卡尔曼滤波，过程噪声0.01、观测噪声0.25 | 192棵树 | 资源充足、数据质量较好的环境 |

三档配置主要改变计算规模和算法参数，不改变闭环建议器的业务阈值。这样从中档切到高档时，使用的计算资源和模型稳定性会变化，但“什么情况下继续执行、什么情况下调整或终止”的业务规则不会被悄悄改变。

默认使用 `medium`。部署时可以通过 `EXECUTION_CONTROL_ALGORITHM_PROFILE` 和 `CLOSED_LOOP_ALGORITHM_PROFILE` 设置，也可以在单次算法请求里传入 `profile`。如果填写了不支持的档位，系统会直接报错，不会静默套用一个看似正常的默认配置。

## 哪些算法没有替换

xBD 毁伤评估本身已经是独立算法服务，所以本次保留现有实现，只完善它与闭环评估链路的调用关系。闭环建议器也没有替换，因为它属于可解释的确定性阈值策略，计算量很小，而且每个阈值都对应明确的业务条件。为了追求“全部开源化”而强行更换这部分，反而可能改变现有业务语义。

本次还评估了 [Google OR-Tools](https://github.com/google/or-tools)。该项目截至2026年9月11日约有14.0k Star，适合解决资源容量、任务时间窗、互斥关系和组合调度问题。但是目前前置 Agent 还没有稳定提供这些完整约束，所以暂时没有正式接入。等后续上游能够提供资源容量、时间窗和任务互斥字段后，再把执行器分配和任务调度建模成 OR-Tools 优化问题会更合理。

## 链路和测试结果

本次新增了覆盖 `low`、`medium`、`high` 三档的完整链路测试，测试过程不是只调用单个算法函数，而是从前置 Agent 结果开始，依次经过执行控制、规则匹配、轨迹预测、控制命令生成、七维特征适配、随机森林评分和闭环建议输出。

| 测试范围 | 通过数量 | 验证内容 |
|---|---:|---|
| 算法服务、三档配置和完整链路 | 33 | 通用算法服务及三档链路是否正常 |
| Commander算法编排 | 8 | 远程调用、本地回退和返回契约 |
| 任务特征模块 | 9 | 七维特征提取和缺失输入处理 |
| 闭环集成 | 12 | 完成度评分及闭环建议生成 |
| 合计 | 62 | 本次改造范围内全部通过 |

算法库与 Commander 本地副本的一致性检查已经通过，Git 差异格式检查也已经通过。目前有一项旧版执行控制集成测试无法收集，是因为当前仓库缺少该测试依赖的 `artillery_agent` 和 `assault_agent` 演示模块，不是本次算法替换造成的。针对实际改造范围，已经增加了不依赖这两个缺失模块的端到端测试。

## 本周结论

目前执行控制和闭环评估中的通用算法已经从 Agent 中解耦，轨迹预测、关联规则挖掘和任务完成度评估也已经替换成 scikit-learn、FilterPy 和 mlxtend 的成熟实现。低、中、高三档配置已经接入，原有输入输出格式和业务决策语义保持不变，完整链路测试共62项通过。

下一步主要是两部分工作。第一部分是获取真实业务标注数据，重新训练任务完成度模型，并对七维特征和闭环阈值进行校准。第二部分是等待上游补充资源容量、时间窗和任务互斥等约束，再判断是否引入 OR-Tools 完成执行器分配和任务调度优化。算法库代码现在已经具备独立提交条件，后续可以同步到 GitHub 算法库分支，Commander 侧继续保留轻量适配和本地回退能力。
