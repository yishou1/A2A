# 算法卡片设计说明

## 1. 文档目的

算法卡片（`algorithm_card.yaml`）是算法包的统一描述文件，位于：

```text
examples/<algorithm_id>/<version>/algorithm_card.yaml
```

它同时服务于四类使用者：

1. **开发人员**：了解算法用途、输入输出、模型文件和运行方式。
2. **Agent**：发现算法能力，判断适用场景，并选择可调用的算法。
3. **算法库运行时**：加载模型或连接 Python 服务，完成输入输出校验和执行。
4. **运维与前端**：展示算法状态、资源要求、性能、安全信息和功能点执行轨迹。

算法卡片不是算法实现本身。真正可调用的算法包还必须包含卡片引用的 Schema、模型或服务、预后处理配置及黄金样例。

## 2. 总体结构

当前正式 `AlgorithmCard` 由以下十类信息组成：

| 类别 | 顶层字段 | 是否必需 | 主要使用者 |
|---|---|---:|---|
| 身份与生命周期 | `algorithm_id`、`version`、`display_name`、`backend_type`、`status` | 是 | 注册表、开发人员 |
| 任务分类 | `task_family` | 是 | Agent、查询接口 |
| 数据模态 | `modalities` | 是 | Agent、输入输出适配 |
| 技术能力 | `capabilities` | 是 | Agent、算法发现接口 |
| 业务功能点 | `operational_functions` | 否，业务算法推荐填写 | Agent、前端流程、审计日志 |
| Agent 语义说明 | `agent_card` | 是 | Agent、开发人员 |
| 机器执行契约 | `machine_spec` | 是 | 注册校验、运行时 |
| 调用限制 | `constraints` | 否 | Agent、网关、运行时规划 |
| 性能与资源画像 | `performance`、`resource_requirements`、`model_profile` | 否 | Agent、调度器、运维 |
| 安全要求 | `safety` | 否 | Agent、审核流程、前端 |

此外，部分算法卡还包含 `provenance`、`algorithm_class`、`algorithm_class_name`、`owner_scope` 等扩展资料。当前 C++ `AlgorithmCard` 尚未正式解析和持久化这些字段，详见第 13 节。

## 3. 身份与生命周期字段

### 3.1 `algorithm_id`

- 类型：字符串
- 必填：是
- 用途：算法的稳定机器标识。
- 建议：采用小写蛇形命名，例如 `edl_evidential_verifier`。
- 约束：同一 `algorithm_id + version + backend_type` 在注册表中构成唯一算法键。

### 3.2 `version`

- 类型：字符串
- 必填：是
- 用途：算法包版本。
- 建议：使用语义化版本，例如 `1.0.0`。
- 要求：目录版本、算法卡版本、服务 `/metadata` 返回版本应保持一致。

### 3.3 `display_name`

- 类型：字符串
- 必填：是
- 用途：供前端和 Agent 展示的可读名称。

### 3.4 `backend_type`

- 类型：枚举字符串
- 必填：是
- 当前支持：
  - `onnx`
  - `python_http_service`
- 要求：顶层 `backend_type` 必须与 `machine_spec.runtime.backend_type` 一致。

### 3.5 `status`

- 类型：枚举字符串
- 必填：是
- 可选值：
  - `draft`：草稿或尚未完成验收。
  - `validated`：已通过算法包校验。
  - `active`：允许被正常查询和调用。
  - `disabled`：保留但暂停调用。
  - `deleted`：逻辑删除。

需要注意：卡片中的 `status` 是算法包声明；注册后注册表还会维护实际生命周期状态。是否能够通过 `/run` 调用，以注册表条目的实际状态为准，必须为 `active`。

## 4. 任务、模态与能力字段

### 4.1 `task_family`

- 类型：字符串
- 必填：是
- 用途：对算法进行粗粒度分类。
- 示例：`detection`、`classification`、`tracking`、`forecasting`、`planning`、`scoring`。
- 查询方式：

```http
GET /algorithms?task_family=classification&active_only=true
```

### 4.2 `modalities`

包含两个非空数组：

```yaml
modalities:
  input:
    - structured_json
    - numeric_features
  output:
    - structured_json
```

- `input`：算法接受的数据类型。
- `output`：算法产生的数据类型。
- 常见值：`text`、`structured_json`、`numeric_features`、`embeddings`、`graph_tensors`。

该字段是面向 Agent 的粗粒度描述，精确结构仍以 JSON Schema 和 ONNX tensor 契约为准。

### 4.3 `capabilities`

- 类型：非空字符串数组
- 必填：是
- 用途：描述算法的技术能力，可用于算法发现和筛选。
- 示例：

```yaml
capabilities:
  - evidential_verification
  - uncertainty_estimation
  - batch_inference
```

查询方式：

```http
GET /algorithms?capability=uncertainty_estimation&active_only=true
```

`capabilities` 表示“算法会做什么技术处理”，不等同于前端流程中的 28 个业务功能点。

## 5. 业务功能点 `operational_functions`

该字段建立算法与 KC-01～KC-28 功能点之间的对应关系，并用于：

- Agent 按业务功能点发现算法。
- `/run` 返回本次执行的功能点。
- 审计日志记录功能点执行状态。
- 前端按 `trace_id` 展示完整流程。

示例：

```yaml
operational_functions:
  - function_id: KC-09
    function_code: validate_detection
    function_name: Validate Detection
    role: primary
    coverage_level: full

  - function_id: KC-15
    function_code: validate_target_threat
    function_name: Validate Target / Threat
    role: supporting
    coverage_level: partial
```

### 5.1 子字段

| 字段 | 是否必需 | 说明 |
|---|---:|---|
| `function_id` | 是 | 标准功能点编号，例如 `KC-09` |
| `function_code` | 是 | 稳定机器编码，例如 `validate_detection` |
| `function_name` | 是 | 前端展示名称 |
| `role` | 否 | 算法在该功能点中的作用，默认 `primary` |
| `coverage_level` | 否 | 覆盖程度，默认 `full` |

### 5.2 `role` 建议值

- `primary`：该算法直接承担该功能点。
- `supporting`：提供特征、评分、预测等支撑结果。
- `orchestrator`：组合多个算法完成该功能点。
- `handoff`：只生成交接信息，由外部系统继续执行。

### 5.3 `coverage_level` 建议值

- `full`：完整覆盖。
- `partial`：只覆盖部分步骤或部分数据类型。
- `advisory`：只提供建议或解释。
- `external_handoff`：实际执行发生在算法库之外。

功能点编号、编码和名称必须与 `config/operational_function_catalog.yaml` 保持一致。KC-23 使用 `handoff + external_handoff`，算法库只记录外部交接完成，不能表示外部动作已经实际完成。

查询方式：

```http
GET /algorithms?function_id=KC-09&active_only=true
GET /algorithms?function_code=validate_detection&active_only=true
```

## 6. Agent 语义说明 `agent_card`

`agent_card` 是算法卡中面向人类和 Agent 的语义层，负责回答“什么时候应该用、什么时候不应该用、输入输出代表什么”。

```yaml
agent_card:
  summary: 简要说明算法用途和核心实现。
  when_to_use:
    - 适用条件一。
    - 适用条件二。
  when_not_to_use:
    - 不适用条件一。
  input_description: 输入字段、单位、顺序和前置条件说明。
  output_description: 输出语义、类别顺序、置信度和限制说明。
  examples:
    - input:
        features: [0.1, 0.2]
      output:
        label: example
```

### 6.1 子字段要求

| 字段 | 是否必需 | 说明 |
|---|---:|---|
| `summary` | 是 | 算法用途和实现概要 |
| `when_to_use` | 是，非空数组 | 适用条件 |
| `when_not_to_use` | 是，非空数组 | 禁用或不适用条件 |
| `input_description` | 是 | 输入业务语义 |
| `output_description` | 是 | 输出业务语义 |
| `examples` | 否 | 供 Agent 理解的输入输出示例 |

编写时应明确单位、特征顺序、类别顺序、前置处理和已知局限，不能只写“参见 Schema”。Schema 描述结构合法性，`agent_card` 描述业务语义和使用边界。

## 7. 机器执行契约 `machine_spec`

`machine_spec` 是运行时真正使用的机器可读配置。

### 7.1 通用字段

```yaml
machine_spec:
  input_schema_ref: input.schema.json
  output_schema_ref: output.schema.json
  tensor_contract_ref: tensor_contract.yaml
  runtime:
    backend_type: onnx
```

| 字段 | 是否必需 | 说明 |
|---|---:|---|
| `input_schema_ref` | 是 | 输入 JSON Schema，相对算法包目录解析 |
| `output_schema_ref` | 是 | 输出 JSON Schema，相对算法包目录解析 |
| `tensor_contract_ref` | ONNX 推荐 | ONNX 输入输出 tensor 名称、类型和形状 |
| `runtime` | 是 | 后端运行配置 |
| `tokenizer` | 否 | 文本模型的 tokenizer 配置 |
| `preprocess` | ONNX 必需 | JSON 到 tensor 的预处理配置 |
| `postprocess` | ONNX 必需 | tensor 到 JSON 的后处理配置 |

### 7.2 ONNX 后端

```yaml
machine_spec:
  input_schema_ref: input.schema.json
  output_schema_ref: output.schema.json
  tensor_contract_ref: tensor_contract.yaml
  runtime:
    backend_type: onnx
    model_uri: model.onnx
    execution_provider: cpu
  tokenizer:
    type: wordpiece
    tokenizer_uri: tokenizer.json
    max_length: 128
  preprocess:
    config_uri: preprocess.yaml
  postprocess:
    config_uri: postprocess.yaml
    label_map_uri: label_map.json
```

ONNX 注册校验要求：

- `model_uri` 非空且模型文件存在。
- `preprocess.config_uri` 和 `postprocess.config_uri` 非空且文件存在。
- 输入输出 Schema 文件存在且属于运行时支持的 Schema 子集。
- 提供 `tensor_contract_ref`、tokenizer 或 label map 时，对应文件必须存在。
- 算法包需要通过 ONNX 加载、tensor 契约和黄金样例校验。

### 7.3 Python HTTP Service 后端

```yaml
machine_spec:
  input_schema_ref: input.schema.json
  output_schema_ref: output.schema.json
  runtime:
    backend_type: python_http_service
    endpoint: http://127.0.0.1:9022/predict
    health_endpoint: http://127.0.0.1:9022/health
    metadata_endpoint: http://127.0.0.1:9022/metadata
    timeout_ms: 3000
```

Python 服务注册校验要求：

- `endpoint`、`health_endpoint`、`metadata_endpoint` 均非空。
- `timeout_ms` 必须大于 0。
- 输入输出 Schema 文件存在且合法。
- 注册或重新校验时服务必须已经启动。
- `/health`、`/metadata` 和黄金样例 `/predict` 联调必须通过。

算法库不会因为卡片中写了 endpoint 就自动启动 Python 服务。

## 8. 调用限制 `constraints`

```yaml
constraints:
  max_input_chars: 2000000
  max_request_bytes: 4194304
  batch_supported: true
  streaming_supported: false
```

| 字段 | 说明 |
|---|---|
| `max_input_chars` | 最大字符数 |
| `max_request_bytes` | 最大请求体字节数 |
| `batch_supported` | 是否支持批处理 |
| `streaming_supported` | 是否支持流式处理 |

这些字段用于 Agent 选型、网关限流和调用前检查。算法输入 Schema 仍是数据结构是否合法的最终依据。

## 9. 性能信息 `performance`

```yaml
performance:
  latency_ms_p50: 2
  latency_ms_p95: 10
  primary_metric: reference_holdout_accuracy
  primary_score: 0.888889
  time_complexity: O(B*T*D)
  space_complexity: O(T*N)
  complexity_variable: B=batch, T=trees, D=depth, N=nodes
  performance_notes: 指标的数据来源和适用边界。
```

| 字段 | 说明 |
|---|---|
| `latency_ms_p50` | 延迟中位数 |
| `latency_ms_p95` | 95 分位延迟 |
| `primary_metric` | 主评估指标名称 |
| `primary_score` | 主指标分数 |
| `time_complexity` | 时间复杂度 |
| `space_complexity` | 空间复杂度 |
| `complexity_variable` | 复杂度符号的业务含义 |
| `performance_notes` | 测试环境、数据集和指标限制 |

性能指标必须说明数据来源。合成数据或参考数据上的分数不能描述成真实业务性能。

## 10. 资源要求 `resource_requirements`

```yaml
resource_requirements:
  min_cpu_cores: 1
  recommended_cpu_cores: 2
  min_memory_mb: 128
  recommended_memory_mb: 256
  min_gpu_count: 0
  gpu_type: optional
  min_vram_mb: 0
  recommended_vram_mb: 0
  disk_mb: 10
```

该部分描述算法运行的最低资源和推荐资源。Agent 或调度器可以结合节点资源筛选算法：

```http
GET /algorithms?max_memory=1024&max_cpu_cores=2&active_only=true
```

主要字段包括 CPU 核数、内存、GPU 数量和类型、显存及磁盘占用，单位均应明确为卡片约定的核数或 MB。

## 11. 模型画像 `model_profile`

```yaml
model_profile:
  parameter_count: 290
  parameter_count_text: 290_small_profile
  flops: 580
  flops_text: approximately 580 FLOPs per sample
  flops_input_shape: [1, 6]
  model_size_mb: 1
  precision: fp32
```

| 字段 | 说明 |
|---|---|
| `parameter_count` | 可精确表示时的参数量 |
| `parameter_count_text` | 参数量或非标准模型规模的文本说明 |
| `flops` | 指定输入形状下的运算量 |
| `flops_text` | FLOPs 估算方法说明 |
| `flops_input_shape` | 计算 FLOPs 时使用的输入形状 |
| `model_size_mb` | 模型文件大小 |
| `precision` | `fp32`、`fp16`、`int8` 等精度 |

树模型、规则模型等不适合用神经网络参数量描述时，应通过文本字段说明统计口径。

## 12. 安全要求 `safety`

```yaml
safety:
  risk_level: medium
  requires_human_review: true
```

- `risk_level`：风险级别，例如 `low`、`medium`、`high`。
- `requires_human_review`：结果进入后续流程前是否需要人工复核。

该字段可供 Agent 决定是否自动继续、前端是否显示审核状态，以及流程编排器是否插入人工确认节点。

## 13. 当前扩展资料字段

部分算法卡还包含以下字段：

```yaml
algorithm_class: M14
algorithm_class_name: 可解释 AI 模型
owner_scope: track_threat_agent

provenance:
  model_artifact_ref: model.onnx
  model_metadata_ref: model.metadata.json
  training_script_ref: ../../../scripts/train_model.py
  dataset_ref: ../../../data/reference_dataset.json
```

这些字段具有明确价值：

- `algorithm_class`：与 M01～M20 算法类别建立对应。
- `algorithm_class_name`：类别展示名称。
- `owner_scope`：所属 Agent 或业务域。
- `provenance`：模型产物、元数据、训练脚本和数据集来源。

但当前实现中它们尚未进入 `AlgorithmCard` C++ 结构，存在以下限制：

- YAML 加载时不会报错，但核心解析器不会保存这些字段。
- 注册表持久化后的 `card` JSON 不包含这些字段。
- `GET /algorithms` 返回的 Agent View 不包含这些字段。
- 不能通过注册表查询条件筛选这些字段。

因此它们目前属于“算法包资料字段”，还不是正式运行契约。后续若前端或 Agent 需要使用，应先扩展 `AlgorithmCard`、序列化、验证器和 Agent View，不能仅依赖 YAML 中存在该字段。

## 14. 算法卡之外的算法包内容

一个完整算法包通常包括：

```text
<algorithm_id>/<version>/
├── algorithm_card.yaml
├── input.schema.json
├── output.schema.json
├── README.md
├── model.onnx 或服务实现
├── model.metadata.json
├── tensor_contract.yaml       # ONNX 可选/推荐
├── preprocess.yaml            # ONNX 必需
├── postprocess.yaml           # ONNX 必需
├── tokenizer.json             # 文本模型可选
├── label_map.json             # 分类模型可选
└── golden_cases/
    ├── case_001_request.json 或 case_001_input.json
    └── case_001_response.json 或 case_001_expected.json
```

各部分职责：

- 算法卡：描述身份、能力、运行方式和治理信息。
- JSON Schema：定义统一 `/run` 的 `inputs` 和 `outputs` 结构。
- tensor 契约：定义 ONNX tensor 名称、类型、形状和顺序。
- 预后处理配置：完成 JSON 与 tensor 之间的转换。
- 黄金样例：证明算法包的声明与实际输出一致。
- 模型元数据与来源资料：记录产物身份、训练和评估依据。

## 15. 注册、Agent 发现与执行关系

```text
algorithm_card.yaml
        │
        ├── 注册/校验：身份、Schema、模型或服务、黄金样例
        │
        ├── 注册表：保存正式 AlgorithmCard 和 Schema 摘要
        │
        ├── Agent View：用途、能力、功能点、资源、性能、安全
        │
        └── /run：选择 backend，校验 inputs，执行并校验 outputs
```

Agent 典型调用流程：

1. 根据任务确定 `capability` 或 `function_code`。
2. 调用 `GET /algorithms` 获取候选算法。
3. 检查 `modalities`、Schema 摘要、资源、性能和安全信息。
4. 选择 `algorithm_id + version + backend_type`。
5. 按输入 Schema 构造 `/run` 请求。
6. 读取算法 `outputs` 和平台返回的 `function_execution`。

前端流程查询：

```http
GET /operational-functions
GET /traces/{trace_id}/function-executions
```

## 16. 字段必填性汇总

### 16.1 所有后端共同必填

- `algorithm_id`
- `version`
- `display_name`
- `backend_type`
- `status`
- `task_family`
- `modalities.input`，至少一项
- `modalities.output`，至少一项
- `capabilities`，至少一项
- `agent_card.summary`
- `agent_card.when_to_use`，至少一项
- `agent_card.when_not_to_use`，至少一项
- `agent_card.input_description`
- `agent_card.output_description`
- `machine_spec.input_schema_ref`
- `machine_spec.output_schema_ref`
- `machine_spec.runtime.backend_type`

### 16.2 ONNX 额外必填

- `machine_spec.runtime.model_uri`
- `machine_spec.preprocess.config_uri`
- `machine_spec.postprocess.config_uri`

### 16.3 Python HTTP Service 额外必填

- `machine_spec.runtime.endpoint`
- `machine_spec.runtime.health_endpoint`
- `machine_spec.runtime.metadata_endpoint`
- `machine_spec.runtime.timeout_ms`，且大于 0

### 16.4 可选但推荐

- `operational_functions`：业务算法推荐填写。
- `agent_card.examples`：复杂输入输出推荐填写。
- `constraints`
- `performance`
- `resource_requirements`
- `model_profile`
- `safety`
- ONNX 的 `tensor_contract_ref`
- 来源资料 `provenance`，当前属于扩展资料字段。

## 17. 完整 ONNX 示例

```yaml
algorithm_id: example_classifier_onnx
version: 1.0.0
display_name: Example Classifier ONNX
backend_type: onnx
status: validated

task_family: classification
modalities:
  input: [structured_json, numeric_features]
  output: [structured_json]

capabilities:
  - example_classification
  - batch_inference

operational_functions:
  - function_id: KC-06
    function_code: classify
    function_name: Classify
    role: primary
    coverage_level: full

agent_card:
  summary: Classifies normalized feature rows with a frozen ONNX model.
  when_to_use:
    - Features have been normalized and arranged in the documented order.
  when_not_to_use:
    - Raw media has not been converted to numeric features.
  input_description: Float32 feature rows in the order documented by input.schema.json.
  output_description: Class indices, labels and confidence values.

machine_spec:
  input_schema_ref: input.schema.json
  output_schema_ref: output.schema.json
  tensor_contract_ref: tensor_contract.yaml
  runtime:
    backend_type: onnx
    model_uri: model.onnx
    execution_provider: cpu
  preprocess:
```

## 18. 编写与评审检查表

- [ ] ID、版本、目录、模型元数据和服务 metadata 一致。
