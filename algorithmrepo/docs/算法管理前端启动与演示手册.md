# 算法管理前端启动与演示手册

## 1. 使用范围

本文用于算法管理界面的日常重新启动和现场演示。推荐从仓库根目录启动所有程序，确保 AlgoLib 使用同一份 `.algolib/registry.json`。

当前 Registry 已纳管 23 个算法：11 个 ONNX、12 个 Python HTTP。注册状态会持久化，重新启动后不需要再次批量注册。

## 2. 每次重新启动的标准流程

建议准备三个 PowerShell 窗口，并按以下顺序启动。

### 2.1 窗口一：启动 Python 算法服务

```powershell
cd D:\bupt\P1\A2A-lkf-algorithmrepo
.\scripts\start_a2a_algorithm_services.ps1
```

脚本会启动多个独立 Python 进程，因此任务栏出现一组 Python 窗口属于正常现象。演示期间不要关闭这些进程，也不要重复执行启动脚本，否则会出现端口占用。

可检查代表性服务：

```powershell
Invoke-RestMethod http://127.0.0.1:9010/health
Invoke-RestMethod http://127.0.0.1:9032/health
```

返回 `ok: true`、`status: ready` 表示服务正常。

### 2.2 窗口二：启动 AlgoLib Server

```powershell
cd D:\bupt\P1\A2A-lkf-algorithmrepo
.\build-smoke-offline\Debug\algolib_server.exe
```

检查后端：

```powershell
Invoke-RestMethod http://127.0.0.1:8088/health
```

### 2.3 窗口三：启动前端

```powershell
cd D:\bupt\P1\A2A-lkf-algorithmrepo\web
npm run dev -- --host 127.0.0.1
```

首次安装或 `package.json` 发生变化时，先执行一次：

```powershell
npm install
```

打开：

```text
http://127.0.0.1:5173/algorithms
```

如果终端提示 Vite 改用了 `5174` 等端口，应以终端显示的 Local 地址为准。

### 2.4 启动后的检查顺序

1. 页面右上角显示“服务正常”。
2. 算法目录显示 23 个算法。
3. 后端类型筛选中可以分别看到 ONNX 和 Python HTTP。
4. 在线调用页面能够看到已激活算法。

如果算法数量重新变成 0 或 11，优先检查 AlgoLib 是否从仓库根目录启动，以及健康接口返回的 `registry_path` 是否指向仓库下的 `.algolib/registry.json`。

## 3. 演示前准备

建议演示一个“目标威胁研判—轨迹预测—规则匹配—合规检查”的辅助决策链路。该演示会使用三个 Python HTTP 算法和一个 ONNX 算法，能够同时展示算法管理、双后端调用、结构化结果和执行链路。

演示前进入“算法目录”，确认并激活以下算法：

| 顺序 | 算法 | 后端 | 展示目的 |
|---:|---|---|---|
| 1 | `threat_priority_random_forest` | Python HTTP | 多目标威胁优先级分类 |
| 2 | `trajectory_linear_predictor` | Python HTTP | 根据历史轨迹预测速度和瞄准点 |
| 3 | `execution_rule_matcher` | Python HTTP | 匹配执行规则并给出建议动作 |
| 4 | `compliance_risk_scorer_onnx` | ONNX | 展示本地模型推理和合规风险概率 |

`compliance_risk_scorer_onnx` 当前已经激活，其余算法如仍为 `validated`，进入详情页点击“激活”即可。

## 4. 推荐的现场讲解流程

### 4.1 展示资产和能力

1. 打开“运行总览”，介绍算法总数、状态、部署和服务健康信息。
2. 打开“算法目录”，分别筛选 ONNX 和 Python HTTP，说明统一算法卡和统一调用协议屏蔽了运行方式差异。
3. 打开“功能点矩阵”，展示 KC 功能点与算法、角色、覆盖程度之间的映射。

### 4.2 建立统一演示链路

进入“在线调用”，本次四次调用都使用：

```text
Trace ID: trace-demo-mission-001
Workflow ID: workflow-demo-mission-001
```

每次切换算法后保留相同 Trace ID 和 Workflow ID，只修改 Step ID，并点击 Request ID 右侧刷新图标生成新的 Request ID。

这样四次独立调用会被记录到同一条执行链路中。当前版本是逐个调用，不是自动工作流编排；业务连续性由相同的 trace/workflow 标识体现。

## 10. 现场演示注意事项

- 提前启动并保留三个终端窗口，不要在演示开始后安装依赖。
- 不要重复运行 Python 服务启动脚本，避免端口冲突。
- 提前激活四个演示算法，并刷新算法目录确认状态。
- 演示时使用 JSON 模式粘贴本文样例，减少复杂数组表单的现场输入时间。
- 每次调用必须刷新 Request ID，但四次调用保持同一个 Trace ID。
- 如果 Python 调用失败，先检查相应 `/health`；如果所有页面都失败，先检查 AlgoLib `8088/health`。
- 当前 Python 启动脚本设置了 `TIA_USE_MOCK=1`。演示时应说明部分高复杂度算法采用仓库参考/模拟运行环境，不应描述为已部署的生产模型服务。


Get-CimInstance Win32_Process |
    Where-Object {
        $_.Name -eq "python.exe" -and
        $_.CommandLine -like "*A2A-lkf-algorithmrepo\services\*"
    } |
    ForEach-Object {
        Write-Host "Stopping PID $($_.ProcessId): $($_.CommandLine)"
        Stop-Process -Id $_.ProcessId
    }
