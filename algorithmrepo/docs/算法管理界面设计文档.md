# 算法管理界面设计文档

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 文档名称 | 算法管理界面设计文档 |
| 适用项目 | A2A 算法库（AlgoLib） |
| 文档版本 | V1.0 |
| 编制日期 | 2026-08-21 |
| 目标读者 | 产品、前端、后端、算法研发、测试和运维人员 |
| 建设阶段 | 管理界面第一版方案 |

## 2. 建设背景与目标

当前算法库已经提供算法注册、查询、生命周期变更、部署实例管理、模型加载与卸载、统一推理、功能点查询和部分执行链路查询接口，但缺少可视化管理入口。算法研发和运维人员主要依赖 CLI、HTTP 请求或直接查看注册表，操作成本较高，也容易混淆算法卡状态、注册表状态和部署状态。

第一版界面定位为 **算法管理与调用控制台**，主要解决以下问题：

1. 统一查看算法目录、版本、后端、能力、资源要求和当前状态。
2. 管理算法的注册、查看、修改、删除、验证、激活和禁用。
3. 管理算法在不同节点上的部署记录以及加载状态。
4. 根据输入 Schema 在线构造请求并验证算法调用结果。
5. 查看算法与 A2A 业务功能点的映射及调用链路。
6. 对删除、禁用和卸载等高风险操作提供二次确认和明确反馈。

第一版不包含模型训练、数据标注、训练任务编排和模型指标实验管理。这些能力当前不属于 AlgoLib 服务端职责。

## 3. 设计原则

- **状态明确**：算法生命周期、算法卡声明状态和部署状态分别展示，不合并为单一状态。
- **操作可控**：激活、禁用、卸载和删除等操作必须校验前置条件，高风险操作需要确认。
- **信息优先**：采用适合高频管理工作的表格和详情页，不采用营销式卡片布局。
- **就近操作**：常用操作放在列表行和详情页顶部，复杂配置使用抽屉或对话框。
- **Schema 驱动**：在线调用表单优先由算法输入 Schema 自动生成，同时提供 JSON 高级模式。
- **后端可信**：界面状态以服务端返回为准；操作完成后重新查询，不进行长期乐观缓存。
- **兼容扩展**：同一 `algorithm_id + version` 可以存在不同后端，界面以三元组作为唯一标识。

算法唯一键定义为：

```text
algorithm_id + version + backend_type
```

## 4. 信息架构

主导航建议包含以下模块：

```text
算法管理台
├── 总览
├── 算法目录
│   ├── 算法列表
│   └── 算法详情
├── 部署管理
├── 在线调用
├── 功能点矩阵
├── 执行链路
└── 系统设置
```

第一版的主要工作流为：

```text
准备算法包
    ↓
注册算法 → 校验算法包 → 激活算法 → 添加部署实例 → 加载模型 → 在线调用
    │                         │               │
    └── 注册失败修正资料       └── 可禁用       └── 可卸载
                                      ↓
                               停止新请求后删除
```

## 5. 状态模型

### 5.1 注册表生命周期状态

注册表生命周期决定算法是否允许通过统一 `/run` 接口调用。

| 状态 | 界面名称 | 含义 | 主要可用操作 |
|---|---|---|---|
| `draft` | 草稿 | 已登记但尚未完成验证 | 查看、编辑资料、验证、删除 |
| `validated` | 已验证 | 算法包校验通过但尚未对外服务 | 查看、重新验证、激活、禁用、删除 |
| `active` | 已激活 | 允许算法发现和统一调用 | 查看、调用、部署管理、禁用 |
| `disabled` | 已禁用 | 保留资料但暂停统一调用 | 查看、重新验证、激活、删除 |
| `deleted` | 已删除 | 逻辑删除，不参与正常查询 | 不在常规列表展示 |

现有代码中的实际状态转换为：

```text
draft ──验证──> validated ──激活──> active
                         └──禁用──> disabled
active ──禁用──> disabled ──激活──> active

任意非 deleted 状态 ──删除──> deleted
deleted 不允许重新验证或激活
```

注册接口当前会先执行算法包校验，注册成功后直接形成 `validated` 注册表条目。因此界面不应假设所有新注册条目都会经历 `draft`。

### 5.2 算法卡声明状态

算法包内 `algorithm_card.yaml` 也包含 `status`。该字段描述算法包资料自身的成熟度，不等同于注册表的实际生命周期。界面在详情页“算法卡”区域展示该值，但列表主状态应使用注册表状态。

### 5.3 部署状态

每个算法可以拥有多个部署实例。部署状态应独立展示：

| 部署状态 | 界面含义 | 推荐颜色 |
|---|---|---|
| `ready` | 实例已就绪 | 绿色 |
| `unloaded` | 已登记但未加载 | 灰色 |
| `loading` | 正在加载（后续扩展） | 蓝色 |
| `error` | 部署或加载失败（后续规范化） | 红色 |

列表页“可调用”判定建议为：

```text
注册表状态为 active
AND
存在可用运行路径（本地 Runner 或 ready 部署实例）
```

对于外部 API 算法，界面额外显示“依赖外部服务”，避免把“已激活”理解成外部 endpoint 一定健康。

## 6. 页面设计

### 6.1 总览页

总览页用于快速判断算法库是否正常，不承担复杂操作。

页面内容：

- 服务状态：服务是否可达、注册表路径、审计日志路径、Runner 缓存数量。
- 算法统计：总数、已激活、已验证、已禁用、草稿数量。
- 后端统计：ONNX、Python HTTP Service 数量。
- 部署统计：部署实例总数、就绪数、未加载数、异常数。
- 风险提醒：无部署实例的激活算法、外部服务不可用算法、长期未验证草稿。
- 最近操作：第一版可暂不提供，待管理审计接口完成后增加。

数据来源：

| 数据 | 接口 |
|---|---|
| 服务健康与 Runner 数量 | `GET /health` |
| 算法及部署统计 | `GET /algorithms?active_only=false` |

当前列表接口没有聚合统计，第一版可由前端对全量结果计算；算法规模增大后应改为服务端聚合。

### 6.2 算法列表页

算法列表是主要工作页面，采用紧凑表格布局。

建议字段：

| 列 | 内容 | 是否默认显示 |
|---|---|---:|
| 算法名称 | `display_name` 和 `algorithm_id` | 是 |
| 版本 | `version` | 是 |
| 后端 | ONNX / Python HTTP | 是 |
| 任务族 | `task_family` | 是 |
| 注册状态 | `active/validated/disabled/draft` | 是 |
| 部署状态 | 就绪实例数 / 总实例数 | 是 |
| 能力 | 前 2 个 capability，其余折叠 | 是 |
| 性能 | 主指标和 P50 延迟 | 可选 |
| 资源 | 最低内存、CPU、显存 | 可选 |
| 操作 | 查看、激活/禁用、更多菜单 | 是 |

筛选条件：

- 关键字：算法 ID 或显示名称。
- 生命周期状态。
- 任务族。
- 后端类型。
- 技术能力 `capability`。
- 业务功能点 `function_id/function_code`。
- 部署节点。
- 最大内存、CPU 核数和显存限制。
- 是否仅显示已激活算法。

当前接口支持除“关键字、分页、排序”以外的大部分筛选。第一版算法数量较少时可在前端完成关键字过滤和排序；正式扩容前应补服务端分页、搜索和排序。

行操作规则：

| 当前状态 | 主操作 | 更多操作 |
|---|---|---|
| `draft` | 验证 | 查看、编辑、删除 |
| `validated` | 激活 | 查看、重新验证、禁用、删除 |
| `active` | 在线调用 | 查看、部署管理、禁用 |
| `disabled` | 激活 | 查看、重新验证、删除 |

列表布局示意：

```text
┌──────────────────────────────────────────────────────────────────────┐
│ 算法目录                                [刷新] [注册算法]            │
├──────────────────────────────────────────────────────────────────────┤
│ 搜索算法...  状态▼  任务族▼  后端▼  能力▼  [重置]                  │
├──────────────────────────────────────────────────────────────────────┤
│ 名称             版本   后端       状态     部署      操作           │
│ 聚类引擎         1.0.0  Python     已激活   1/1 就绪  [调用] [...]   │
│ 决策推荐         1.0.0  ONNX       已验证   0/1 就绪  [激活] [...]   │
│ 目标检测         1.0.0  Python     草稿     0/0       [验证] [...]   │
└──────────────────────────────────────────────────────────────────────┘
```

### 6.3 算法详情页

详情页顶部固定显示算法唯一键、注册状态、算法卡状态、部署摘要及主要操作。

建议标签页：

1. **概览**：用途摘要、适用/不适用场景、能力、任务族、模态、限制和安全等级。
2. **输入输出**：输入 Schema、输出 Schema、字段说明和输入输出示例。
3. **性能资源**：主指标、得分、延迟、复杂度、模型大小、参数量和资源要求。
4. **业务功能点**：KC 功能点、角色和覆盖程度。
5. **部署实例**：节点、区域、endpoint、健康地址、状态、更新时间及部署操作。
6. **在线调用**：Schema 表单、JSON 编辑器、结果和错误信息。
7. **算法卡**：完整结构化算法卡和原始 JSON 视图。

详情页的操作按钮根据状态动态显示，不允许用户提交明显不合法的状态转换。

### 6.4 注册算法

现有注册接口接收服务端本地的 `package_or_card_path`，因此第一版注册对话框采用“服务器路径注册”。

表单字段：

| 字段 | 必填 | 说明 |
|---|---:|---|
| 算法包路径 | 是 | 服务端可访问的算法包目录或算法卡路径 |
| 注册后查看详情 | 否 | 默认开启，成功后跳转详情页 |

操作流程：

```text
输入服务器路径
  → 提交 POST /algorithms/register
  → 服务端校验算法卡、Schema 和包结构
  → 成功：展示唯一键和 validated 状态
  → 失败：展示错误码、错误消息和待修正字段
```

注册成功不自动激活。界面应明确提供“继续激活”按钮，由用户确认后执行。

后续建议增加算法包上传接口，支持上传 ZIP、服务端解压到隔离目录、扫描安全校验、预校验和正式注册。不能让浏览器提交任意服务端路径作为长期生产方案。

### 6.5 修改算法

“修改”需要区分三种对象：

#### 6.5.1 修改算法元数据

包括显示名称、能力、说明、Schema、性能和资源要求。现有服务端没有直接编辑算法卡的 API，当前可行流程是：

```text
在受控代码/文件流程中修改 algorithm_card.yaml 或相关 Schema
  → 在界面执行“重新验证”
  → 服务端从 card_path 重新读取资料
  → 保留已有部署记录并刷新算法卡元数据
```

第一版界面应将该功能命名为“重新验证/刷新资料”，不提供看似可保存但实际无法持久化的编辑表单。

正式支持在线编辑时，建议新增：

```http
PATCH /algorithms/{id}/{version}/{backend}/card
```

要求服务端完成字段白名单、Schema 校验、并发版本控制、变更审计和原文件备份。算法 ID、版本和后端属于唯一键，不允许直接修改；如需改变，应创建新版本或新条目。

#### 6.5.2 修改部署实例

现有接口支持新增部署实例及修改部署状态，但不支持完整更新 endpoint、node、zone 等字段。第一版可采用“删除部署记录后重新添加”，但必须在界面给出明确提示。

后续建议新增：

```http
PATCH /algorithms/{id}/{version}/{backend}/deployments/{deploy_id}
```

#### 6.5.3 修改运行参数

运行参数属于单次调用，不写回算法卡。在在线调用页编辑 `params`，随 `/run` 请求提交。

### 6.6 验证算法

验证操作用于重新读取和校验算法包资料。

界面行为：

1. 点击“验证”或“重新验证”。
2. 弹窗说明验证会刷新算法卡及 Schema 元数据，但保留部署记录。
3. 调用生命周期验证接口。
4. 成功后刷新详情；失败时展示服务端结构化错误。

接口：

```http
POST /algorithms/{id}/{version}/{backend}/validate
```

验证不代表模型已经加载，也不代表外部服务健康。验证结果区域应分别展示“包资料验证”和“运行可用性”。

### 6.7 激活与禁用

激活表示允许算法被查询和通过 `/run` 调用。

激活前检查：

- 注册表状态必须为 `validated` 或 `disabled`。
- 提示用户确认算法运行依赖是否已经准备好。
- 对 Python HTTP 算法显示 endpoint；对 ONNX 算法显示模型文件和部署信息。
- 后续服务端可增加强制健康检查门控。

接口：

```http
POST /algorithms/{id}/{version}/{backend}/activate
POST /algorithms/{id}/{version}/{backend}/disable
```

禁用确认文案需要说明：禁用后新的统一调用将被拒绝，但不会自动删除算法包或部署记录。禁用和卸载是两个独立动作，界面可在禁用成功后询问是否同时卸载 Runner。

### 6.8 删除算法

删除属于高风险操作，入口放在“更多”菜单底部并使用危险样式。

删除前建议执行以下检查：

1. 当前是否为 `active`，如是则建议先禁用。
2. 是否存在 `ready` 部署实例，如有则建议先卸载。
3. 显示算法唯一键，要求用户二次确认。
4. 要求输入算法 ID 或删除确认词，防止误操作。

接口：

```http
DELETE /algorithms/{id}/{version}/{backend}
```

当前实现为逻辑删除，注册表状态变为 `deleted`，并使对应 Runner 缓存失效；不会自动删除算法包物理文件。界面不得显示“文件已永久删除”。

删除完成后返回算法列表，并提供操作结果和 request/trace 信息（待管理审计补充）。

### 6.9 部署管理

部署页既可以展示全部算法部署，也可以嵌入算法详情页。

部署实例字段：

- `deploy_id`
- `node_id`
- `zone`
- `endpoint`
- `health_endpoint`
- `deploy_status`
- `status_message`
- `local_model_path`
- `deployed_at`
- `updated_at`

支持操作：

| 操作 | 当前支持 | 接口 |
|---|---:|---|
| 添加部署实例 | 是 | `POST .../deployments` |
| 删除部署实例 | 是 | `DELETE .../deployments/{deploy_id}` |
| 修改部署状态 | 是 | `PATCH .../deployments/{deploy_id}/status` |
| 完整编辑部署配置 | 否 | 需要新增接口 |
| 加载模型/连接池 | 是 | `POST /load` |
| 卸载模型/连接池 | 是 | `POST /unload` |

加载表单根据后端动态变化：

- ONNX：部署 ID、传输模式、源地址、目标目录、待拉取文件。
- Python HTTP：部署 ID、连接池大小、连接池等待超时。

加载成功后服务端会将部署状态更新为 `ready`；卸载后更新为 `unloaded`。界面完成操作后应重新获取算法详情和 `/health`，同步部署状态及 Runner 缓存数。

### 6.10 在线调用

仅对注册表状态为 `active` 的算法开放主调用按钮。

调用区提供两种模式：

- **表单模式**：依据输入 Schema 生成字段控件，适合常规调试。
- **JSON 模式**：编辑完整 `inputs` 和 `params`，适合复杂嵌套数据。

公共请求字段：

| 字段 | 说明 |
|---|---|
| `request_id` | 默认自动生成，可手动修改 |
| `trace_id` | 默认自动生成，用于关联调用链 |
| `algorithm_id` | 从当前算法带入，只读 |
| `version` | 从当前算法带入，只读 |
| `backend_type` | 从当前算法带入，只读 |
| `deploy_id` | 可选择指定部署实例 |
| `inputs` | 算法输入 |
| `params` | 可选运行参数 |
| `function_context` | 可选 A2A 功能点上下文 |

调用结果区域展示：

- 成功/失败状态和总耗时。
- `outputs` 格式化 JSON。
- `usage` 执行信息。
- request ID、trace ID、算法版本和后端。
- 错误码及错误消息。
- 功能点执行信息。
- 一键复制请求或响应。

涉及敏感输入输出时，不应在浏览器本地存储完整数据。调用历史第一版仅保留当前页面会话。

### 6.11 功能点矩阵

以 KC 功能点为行、算法为关联项，展示：

- 功能点编号、编码和名称。
- 关联算法数量。
- 算法角色：`primary/supporting/orchestrator/handoff`。
- 覆盖程度：`full/partial/advisory/external_handoff`。
- 算法当前是否激活和是否有就绪部署。

数据接口：

```http
GET /operational-functions
GET /algorithms?function_id={function_id}&active_only=false
```

### 6.12 执行链路

第一版提供按已知 `trace_id` 查询：

```http
GET /traces/{trace_id}/function-executions
```

页面以时间线形式展示序号、功能点、算法、版本、后端、状态、延迟和错误码。

当前后端不能列出全部执行历史，也不能按算法、时间和状态筛选。因此“执行记录列表”和趋势统计需要新增审计查询 API 后再建设。

## 7. CRUD 与生命周期能力矩阵

| 管理能力 | 用户界面 | 当前后端支持 | 第一版处理 |
|---|---|---:|---|
| 新增算法 | 注册算法对话框 | 是 | 使用服务器路径注册 |
| 查询算法列表 | 算法目录 | 是 | 支持现有多维筛选 |
| 查询算法详情 | 算法详情页 | 是 | 展示 entry 与 agent_view |
| 修改算法卡 | 详情编辑 | 否 | 只读，提供重新验证 |
| 删除算法 | 删除确认框 | 是 | 逻辑删除 |
| 验证算法 | 验证按钮 | 是 | 支持验证及错误展示 |
| 激活算法 | 激活按钮 | 是 | 按状态显示 |
| 禁用算法 | 禁用按钮 | 是 | 二次确认 |
| 添加部署 | 部署抽屉 | 是 | 支持 |

## 9. 前后端数据与交互约定

### 9.1 刷新策略

- 列表和详情默认使用短时缓存。
- 生命周期、部署、加载和卸载操作成功后立即使相关缓存失效并重新请求。
- 总览健康状态可每 15 秒刷新一次；页面不可见时暂停轮询。
- 在线调用不自动重试，避免重复执行有副作用的算法。
- 查询类请求可对网络错误执行一次有限重试。

### 9.2 错误展示

错误提示需要包含：

- 用户可理解的中文摘要。
- 服务端 `error_code`。
- 服务端原始 `message`。
- 对应操作和算法唯一键。
- 可选 request ID 或 trace ID。

字段校验错误直接显示在对应表单字段下；网络错误和服务不可达使用全局提示；生命周期冲突在弹窗内说明当前状态和允许操作。

### 9.3 空状态

- 无算法：展示“注册算法”入口。
- 筛选无结果：保留筛选条件并提供“重置筛选”。
- 无部署：展示“添加部署实例”。
- 无执行链路：说明 trace ID 不存在或该调用没有功能点记录。
- 服务不可达：页面保持最近一次数据但明确标记为过期，不允许变更操作。

## 10. 基础安全要求

1. 生产环境由同源网关代理前端和 AlgoLib API，不直接向公网暴露 C++ 服务。
2. 注册路径、模型路径和文件下载路径必须继续由服务端进行目录边界校验。
3. endpoint 中的凭据、令牌和查询参数不得在界面明文展示或写入浏览器日志。
4. 在线调用默认不持久化原始输入输出，只展示当前会话结果。
5. 外部 API 凭据通过服务端环境或密钥管理系统注入，前端不接触密钥。
6. 删除、禁用、卸载和部署删除等操作必须二次确认，并明确展示影响范围。

## 12. 前端技术建议

建议采用以下技术栈：

- React + TypeScript + Vite。
- React Router 管理路由。
- TanStack Query 管理请求、缓存和操作刷新。
- TanStack Table 或 Ant Design Table 实现算法及部署表格。
- React Hook Form 管理注册、部署和调用表单。
- AJV 根据 JSON Schema 进行输入校验。
- Monaco Editor 或轻量 JSON Editor 提供高级 JSON 模式。
- Vitest + Testing Library 进行组件测试。
- Playwright 验证注册、激活、加载、调用、禁用等关键路径。

### 阶段二：生命周期与部署

## 14. 第一版验收标准

1. 能正确列出注册表中的全部非删除算法，并展示唯一键和生命周期状态。
2. 能按状态、任务族、后端、能力和业务功能点筛选算法。
3. 能查看任意算法的算法卡、Schema、资源要求和部署实例。
4. 能通过服务端路径注册一个合法算法包，并清晰展示校验错误。
5. 能完成验证、激活、禁用和逻辑删除，并遵守状态转换约束。
6. 能新增和删除部署实例，并完成加载及卸载。
7. 能根据输入 Schema 发起 `/run` 请求，并展示成功结果或结构化错误。
8. 能通过 trace ID 查看功能点执行链路。
9. 所有危险操作均有二次确认，并明确提示操作影响。
10. 服务不可达时禁止变更操作，页面不存在状态误导或敏感信息泄露。

## 15. 方案结论

第一版优先建设可落地的算法管理闭环：**查询 → 注册 → 验证 → 激活 → 部署/加载 → 调用 → 禁用/删除**。现有 AlgoLib 接口可以支撑大部分核心流程，但“在线编辑算法卡、算法包上传、完整部署编辑和执行历史列表”仍需补充服务端能力。

界面实现时应始终将算法卡状态、注册表生命周期和部署状态分开表达，并以注册表 `active` 状态作为是否允许统一调用的主要依据。
